# 课程设计和写作规则

这些规则来自一门 22 课的 Kafka 课程，经过逐课讨论、复查和修订。目标读者是**初学者**：懂一点编程和服务，但没用过这项技术。

## 1. 大纲：故障驱动、循序渐进
- **每课从一个真实的生产故障开始**，再引入解决它的机制。读者先感受到「痛」，才会在意「药」。
- **一条贯穿始终的业务场景**（比如订单系统：Order Service → 主题 → Inventory / Notification / Shipping）。所有课用同一批服务名，读者不用每课重新认识角色。
- **每课只引入一两个新概念**。还没讲到的概念不要提前用；非用不可时用描述代替（第 1–3 课说「待读取」，第 4 课才引入 Lag）。
- **衔接**：每课开头说清楚和上一课的关系（「第 6 课说 RF=3 能扛住宕机，可它不保证消息不丢……」）。前面课程里的简化说法，后面要明确纠正（「第 2 课说轮流写入，其实……」）。
- **概念归属唯一**：一个参数只在一课里详细讲（比如 acks 归第 7 课），其他课引用「第 7 课」，不重复展开。
- 大纲表格包含：课号、标题、开场故障、新概念、依赖哪几课。**先给用户确认大纲再写课。**

## 2. 每课的结构
| 部分 | 内容 |
|---|---|
| 标题 | 「概念：一个具体问题？」 |
| problem（引言） | 一两句话的真实故障 |
| 01 故障现场 + 场景 A | 没有这个机制时会怎样；告诉读者点哪个按钮 |
| 02 引入核心机制 + 场景 B | 机制怎么解决；可切换的模式 / 参数，对比不同选择 |
| 03 故障模拟与处理边界 | 这个机制管不到什么，还会怎么坏 |
| 进阶（可选） | 不值得单开一课、但上线需要知道的内容 |
| 04 知识复盘 | 3–4 张概念卡 + 一张对比表 + 本课一句话 |
| 05 小测试 | 一道情境题 + 解析 |

第 1 课通常是「为什么需要这项技术」，可以不设小测试（review.quiz = false）。

## 3. 场景图怎么设计
- **A、B 两张图用同一套布局**，只改状态和工具栏，读者一眼看出差别。
- **每张图都有能点的按钮**，按钮制造故障或切换方案，比如「让 Notification 宕机」「先升级 Producer」。读者点了才会看到问题，不要只放自动播放的动画。
- **旁白跟着状态变**：每种情况一段，说清「看到了什么 → 为什么 → 意味着什么」，红 / 橙 / 绿表示坏 / 警告 / 好。
- **画面里出现的数字要和指标区一致**，并在 note 里说明换算（「画面 1 秒 ≈ 真实 1 分钟」「按每秒 12,000 条换算」）。
- **终端 / 命令行输出要真实**：用真实的命令、真实的报错名（SerializationException、NotEnoughReplicas）。
- 颜色含义全课统一：橙 = 待处理 / 警告，红 = 出错 / 丢失，黄 = 重复 / 重读，灰 = 已删除 / 空闲，蓝 = 当前 / Leader。

## 4. 写作规则
- 中文为主，技术名词保留英文（Partition、Offset、Consumer Group）；参数名、命令用 `<code>`。
- 短句，主动语态；先结论后原因。避免「赋能、抓手、闭环」之类空话。
- 一段只讲一件事；举例用课程场景里的服务和数字。
- 复盘卡的 `scene` 字段要指回图里的元素，把文字和画面连起来。
- 交叉引用写「第 N 课」，改课号时记得全文搜索。

## 5. 小测试规则
- **每课 1–3 题**（`quiz` 数组）：第一题考本课的核心机制，其余考边界或常见误用。题多了读者会跳过。
- **情境题**：给出具体的数字和配置，问「会发生什么 / 该怎么做」，不要问定义。
- **4 个选项，干扰项是常见误解**（「加实例就能更快」「acks=all 只要 Leader 确认」），不要放一眼能排除的离谱选项（「删除 Topic」）。
- **正确答案在 A–D 之间分散**，全课大致平均。检查脚本会统计分布。
- **每题写 explain**：为什么对，其他选项错在哪里，必要时指回某一课。
- 措辞和正文一致，不用缩写（写「min.insync.replicas = 2」，不写「minISR=2」）。

## 6. 准确性：版本、默认值、绝对化表述
- **版本号和默认值**（「Kafka 3.0 起默认开启」「默认 45 秒」）要查证。能联网就查官方文档；查不到就在交付时明确告诉用户哪几条没核实。
- **避免绝对化**：「同一个 Key 永远落在同一个 Partition」要加条件（Partition 数和分区规则不变时）。「exactly-once」要说清楚范围。
- **区分「首次连接」和「运行中」**之类容易混淆的场景（例：bootstrap.servers 只用于首次连接和发现集群）。
- 不确定的地方宁可少说，不要编。

## 7. 全课复查清单
全部写完后，按这个清单复查一遍，并把发现列给用户：
1. 交叉引用：每处「第 N 课」都指向讲了这个内容的课。
2. 绝对化表述、版本和默认值（第 6 节）。
3. 小测试：答案分布、干扰项质量、措辞、每题有解析。
4. 一致性：服务名、系列名、颜色含义、术语译法前后一致。
5. 页面：两处「本课一句话」不重复；终端里错误用红色。
6. `check.js` 全课通过（重叠、遮挡、报错、定时器、手机宽度、小测试）。
7. 缺口：对照这项技术上线常见的问题，看有没有漏掉的重要主题（可以用「进阶」卡补，不打乱课号）。
